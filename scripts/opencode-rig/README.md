# opencode test rig

Run **one** opencode session the way the clankerbar fleet runs it, with every
outside dependency replaced:

| Fleet dependency | What the rig substitutes |
|---|---|
| the session config in `OPENCODE_CONFIG_CONTENT` | generated by the CLI's own `harness.OpencodeSessionConfig`, so the permission policy, the MCP servers out of Code Mode and the agent pins are the fleet's |
| the clankerbar MCP server | a local stdio **stub** serving the plane's real `tools/list` (fetched read-only, or from a file) and canned responses; it never opens a backlog connection |
| the provider | an in-process **logging proxy** in front of the real provider, recording each request body and response (never the `Authorization` header) |
| the operator's opencode data/state/cache | its own `XDG_DATA_HOME` / `XDG_STATE_HOME` / `XDG_CACHE_HOME` under the run directory |

It exists so a question about a model, a provider or a tool schema can be
answered in one small run with the evidence on disk, instead of a live fleet
run whose transcript scrolls away.

```
scripts/opencode-rig/run.sh --model commandcode/gpt-6-luna --scenario padding
```

Each run prints a report and leaves its raw logs in the run directory. **Every
run makes real provider requests and costs real money** (see [Cost](#cost)).

## Quick start

```bash
# the fleet model and its key (the key file is where the daemon keeps it)
export COMMANDCODE_API_KEY="$(cat ~/.config/clankerbar/commandcode-key)"

# reproduce the Luna padding question against Command Code
scripts/opencode-rig/run.sh \
  --model commandcode/gpt-6-luna \
  --scenario padding \
  --deadline 3m --max-tool-calls 4
```

`run.sh` builds and runs the Go program with `go run`; nothing is installed.
The report goes to stdout and to `<out>/report.md`.

Useful flags (full list: `run.sh --help`):

| Flag | Meaning |
|---|---|
| `--model provider/model` | **required**; the fleet model, e.g. `commandcode/deepseek/deepseek-v4.1-flash`. The provider part also selects which `baseURL` is redirected at the proxy |
| `--scenario` | `padding` (default), `reasoning-replay`, `schema` |
| `--schemas live\|file` | tool catalog: fetch the plane's real `tools/list`, or serve a file (the `schema` scenario) |
| `--mcp-config` | source config; defaults to `~/.config/clankerbar/opencode-mcp.json` when present, otherwise a minimal config with only the stub |
| `--config-dir` | `OPENCODE_CONFIG_DIR` for the session; pass `~/.config/opencode` for a fleet-identical global layer |
| `--upstream` | the real provider base URL, if the config does not declare `provider.<id>.options.baseURL` |
| `--plane-key-file` | read `CLANKERBAR_API_KEY` from a file (for the read-only schema fetch) |
| `--provider-key-file` | read the provider key from a file and set `COMMANDCODE_API_KEY` (`--provider-key-env` names another variable); `--env KEY=VALUE` passes others |
| `--deadline` | kill the session after this (default `5m`) |
| `--max-tool-calls` | stop after this many stub calls (default `6`; `0` = no cap) |
| `--out` | run directory (default `$TMPDIR/opencode-rig/<scenario>-<UTC stamp>`) |
| `--dry-run` | resolve the config, port, catalog and prompt; print them; spawn nothing |
| `--prompt` | override the scenario's prompt |

`--config-dir ~/.config/opencode` is worth passing for fleet fidelity, but note
that it also loads whatever servers that global layer declares (e.g. `github`).

## Scenarios

### `padding` — what keys does the model send on a review-shaped `update_task`?

The plane's `update_task` takes a nullable `review` block and many nullable
top-level fields. Some models pad a review call with every nullable property set
to `null`, and the plane refuses that as `invalid_review` ("a review call
carries only taskId, runId and review — resend it without: …").

The stub serves `update_task` and refuses it **exactly like the plane** (the
real refusal text, naming the extra arguments the call actually carried). The
report prints the top-level keys sent per call, marking explicit nulls:

```
| # | tool          | keys sent                                        | result                 |
| 1 | `update_task` | `priority=null`, `review`, `runId`, `status=null`, `taskId` | error `invalid_review` |
```

That is the Command Code Luna padding, visible without a fleet run:

```bash
scripts/opencode-rig/run.sh --model commandcode/gpt-6-luna --scenario padding
```

### `reasoning-replay` — does the provider replay `reasoning_content`?

Two tool turns. opencode replays the assistant message that carried the first
tool call on the second request; whether that message still has
`reasoning_content` is provider behaviour. The report prints every assistant
message's extra fields per request:

```
- `[2] assistant`: content=null, tool_calls=1, extras: `reasoning_content`=string(3121)
```

and a one-line observation (`reasoning replay: 1 of 1 assistant message(s) …`).
For DeepSeek via Command Code on 2026-10-21 it was replayed — 127 characters on
one padding run — and replayed as an empty string on steps where the model
produced no reasoning. The report prints the string's length, so `string(0)`
means "replayed, but empty".

```bash
scripts/opencode-rig/run.sh --model commandcode/deepseek/deepseek-v4.1-flash \
  --scenario reasoning-replay
```

### `schema` — test a proposed tool shape before the plane ships it

`--schemas live` (the default) serves the plane's current 29 tools, byte for
byte as fetched. To test a proposal, fetch the catalog once, edit a copy, and
serve it:

```bash
# keep the exact current catalog
scripts/opencode-rig/run.sh fetch-schemas --out /tmp/schemas-live.json

# copy it, change update_task's status to a nullable enum, add a new tool, then:
scripts/opencode-rig/run.sh \
  --model commandcode/deepseek/deepseek-v4.1-flash \
  --scenario schema \
  --schemas /tmp/schemas-proposed.json
```

The scenario asks for `clankerbar_<--schema-tool>` (default `update_task`) with
a null on the optional fields; the report shows the tool catalog that went on
the wire (count, names, one sha256 per request) and whether the model's call
arrived at the stub. A provider or model that rejects the schema fails the run
before any backlog write is possible — there is no backlog connection at all.

`scripts/opencode-rig/testdata/schema-proposed.json` is a small example of an
alternative catalog. It is *not* the live catalog; use `fetch-schemas` for that.

## What a run does

1. **Resolves the tool catalog.** `live` performs a read-only MCP handshake
   against `--plane-url` (`initialize`, `notifications/initialized`,
   `tools/list`) with `CLANKERBAR_API_KEY`, and writes the exact result to
   `<out>/schemas.json`. It never calls a tool.
2. **Builds the source config.** Starts from `--mcp-config`, replaces the
   `clankerbar` MCP server with the rig's own stdio stub, and points the
   selected provider's `options.baseURL` at the local proxy. Everything else in
   the fleet config (reasoning effort, other providers, disabled servers) is
   preserved.
3. **Generates the session config through the CLI.** `session-config` calls
   `harness.OpencodeSessionConfig(...)` — the same function doctor uses — and
   writes the result to `<out>/opencode-config-content.json`. That is what
   `OPENCODE_CONFIG_CONTENT` carries; `OPENCODE_CONFIG` carries the source file.
4. **Binds the proxy on port 0** (`127.0.0.1:0`) before anything else runs, so
   the port is free and the listener is already accepting. There is no
   readiness sleep.
5. **Starts `opencode serve` and waits for the MCP connection.** The rig starts
   the private server with the pinned config, polls `/api/mcp` until the
   `clankerbar` stub reports `connected`, and only then attaches
   `opencode run --server …`. See [traps](#traps-found-the-hard-way).
6. **Runs `opencode run` with stdin from `/dev/null`**, a deadline and a
   tool-call cap, in its own process group.
7. **Reports.** `<out>/report.md` (also printed): tool calls with their keys,
   reasoning tokens per `step_finish`, and every provider request with its
   assistant messages' extra fields. Raw logs sit beside it.

### Isolation

- `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` are per-run directories
  under `<out>/xdg/`. opencode's session database and logs never touch the
  fleet's or the operator's.
- The session's workdir (`<out>/sandbox` unless `--workdir`) is an empty
  directory, and the adapter's permission policy scopes reads/edits to it. The
  model cannot read the repo you launched the rig from.
- The stub logs every `tools/call` and writes nothing else. The rig binary
  contains no plane client beyond the read-only schema fetch.

## Traps found the hard way

These are real failures, each of which cost time. The rig guards against them;
read them before changing the rig or writing a similar harness.

### `opencode run` hangs on an open stdin

If stdin is neither a TTY nor closed, `opencode run` waits forever: no output,
no provider request, no log line after "cli starting". It was first
misattributed to a schema change. The rig always runs the session with
`Stdin = os.DevNull`; the shell equivalent is `< /dev/null`.

### The MCP connection is asynchronous — wait for it, then attach

opencode 2.x connects MCP servers in the background while `opencode run`
submits the first model turn. On 2026-10-19 that race gave two review-panel
members no clankerbar tools at all; the fleet fixed it with a preflight
(`internal/harness/opencode_mcp.go`, CLA-703). **The rig hit the same race on
its first live run**: the model answered "no clankerbar MCP tools are exposed in
this session (only edit, glob, grep, read, shell, write)". The fix, mirrored
from the fleet, is to start `opencode serve`, poll `/api/mcp` until
`clankerbar` reports `connected`, and only then attach `run --server`.

Two details that matter: `/api/mcp` is keyed by **the resolved workdir** (on
macOS `/var` is a symlink to `/private/var`, so querying the raw path reports a
different location as connected), and `run` authenticates to the server with
`OPENCODE_PASSWORD`. The server's `server password …` announcement line is
never written to the run's logs.

### Never hard-code a port

Bind port 0 and read the chosen port back. A stray local server on a fixed
port received a request carrying the provider key; the kernel cannot hand you
an occupied port.

### Readiness is not a sleep

The proxy's listener is bound before the session starts, so "is it up?" is a
property of the process, not a guess. The MCP wait above is a poll with a
deadline, not a fixed delay.

### Bound the session twice

- `--deadline` kills the whole process group (opencode and the stub it spawned)
  after SIGTERM and a grace period.
- `--max-tool-calls` makes the stub refuse the call after the cap and write
  `<out>/stub-capped`; the rig polls that marker and stops the session. A
  looping model cannot spend without limit.

### Logs: capture per run, never read the shared file

opencode's default log (`~/.local/share/opencode/log/opencode.log`) is shared
and busy. The rig passes `--print-logs` to both `serve` and `run`, captures
stderr to `opencode-server-stderr.log` / `opencode-stderr.log`, and points
`XDG_DATA_HOME` at the run directory. Nothing has to be filtered out of a
shared file; the run directory is the filter.

### One run, one directory

A run directory that already holds a `run.json` is refused. Reusing a directory
mixes two runs' evidence and can let a stale `stub-capped` marker stop a healthy
session.

## Cost

**Every real run makes real provider requests.** Nothing here is mocked at the
provider: the proxy forwards to the URL the fleet config declares, with the
provider key the caller supplies.

Measured on 2026-10-21 with `commandcode/deepseek/deepseek-v4.1-flash`, 29
clankerbar tools plus six built-ins:

- one `padding` run with one tool call: **~60–90 KB per request** (the prompt and
  catalog decide), one 13.8 K-token step, **~$0.002**;
- opencode also issues a small title-generation request (no tools, ~3 KB);
- the `reasoning-replay` scenario makes two tool turns and measured **~$0.002**
  in total, with the second request mostly served from the prompt cache;
- the `schema` scenario with a two-tool catalog measured **~$0.0007**.

The caps are the spend bound: the session stops at `--max-tool-calls` calls or
`--deadline`, whichever comes first. Start with `--max-tool-calls 2` and a
3-minute deadline, and use `--dry-run` while wiring a new provider or config.
A run that never reaches the provider costs nothing.

## Tests

```bash
go test ./scripts/opencode-rig/   # model-free: stub, proxy, schemas, report, orchestration
go vet ./scripts/opencode-rig/
```

The suite drives the real stdio stub over JSON-RPC, the real proxy handler
against a local fake upstream, and the session loop against a fake `opencode`
binary (deadline, cap, stdin, env, event capture). No test needs a model, a
network, or a provider key.
