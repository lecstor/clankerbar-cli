## Review: CLA-374 process-group kill (a2338d5 + ef349af)

**Verdict: does not ship as-is.** The core mechanism is right and the tests genuinely pin it (I mutation-tested: with `killProcessGroup`/`setupProcessGroup` neutered, both new tests fail in ~2.5s naming the survivor). But the opencode half introduces a data race that turns CI red on every run, and it is not merely cosmetic.

### What I verified

- `go test ./internal/harness/ -run ProcessGroup -count=1` passes (6.0s / 4.1s).
- Full `go test ./...` (no race) passes.
- `go vet ./...`, `GOOS=windows go build ./...`, `GOOS=linux go build ./...` all clean.
- Mutation test (neutered helper, copy in /tmp): both new tests fail, correctly.
- `go test -race ./internal/harness/` **FAILS** on this branch and **passes** on base `30bd9c5`.

---

### [HIGH] internal/harness/opencode.go:299-304 (with processgroup_unix.go:24-25) - data race on `cmd.Process`, CI-breaking

The monitor goroutine is started *before* `cmd.Run()` (line 324) and reads `cmd.Process` with no happens-before edge to `Start`'s write of it. Verified, deterministic (3/3 runs), and it takes four tests down:

```
WARNING: DATA RACE
Read at 0x... by goroutine 21:
  harness.killProcessGroup()      processgroup_unix.go:24
  harness.opencode.runSession.func2()  opencode.go:302
Previous write at 0x... by goroutine 20:
  os/exec.(*Cmd).Start()  exec.go:733
```

Failing under `-race`: `TestOpencodeProcessGroupKillTerminatesAGrandchild`, `TestOpencodeInvokeEndsASessionThatOutlivesItsWallClockCap`, `TestOpencodeCallerCancellationIsNotAWallClockCap`, and `TestOpencodeWallClockKillDoesNotHangOnAGrandchildHoldingTheStream` - the last of which is the "existing WaitDelay hang test still passes" clause of the bar. `.github/workflows/ci.yml` runs `go test -race ./...` as a required check, so this branch cannot go green.

Suspected (not observed) worst case, which is why I rate this high rather than "CI hygiene": under an unsynchronised read on arm64 the goroutine can observe a non-nil `cmd.Process` whose `Pid` has not been published yet. `syscall.Kill(-0, SIGKILL)` is `kill(0, SIGKILL)`, which POSIX defines as "every process in the *caller's* process group" - i.e. SIGKILL to clankerbar-cli itself and whatever else shares its group. The `cmd.Process != nil` guard does not cover that.

**Fix:** drop the goroutine entirely and use `exec.Cmd.Cancel`, which os/exec calls under its own synchronisation after `Start` has published `Process`:

```go
cmd.Cancel = func() error {
    killProcessGroup(cmd)
    return cmd.Process.Kill()
}
```

That is one line, is race-free by construction, fires on every cancellation of `sctx`, and removes the "goroutine outlives the process" problem below. Independently, harden the helper: `if cmd.Process != nil && cmd.Process.Pid > 0`.

### [MEDIUM] internal/harness/claude.go:96, internal/harness/opencode.go:270 - Ctrl-C no longer reaches the session or its subtree

`Setpgid: true` takes the child out of the terminal's foreground process group. Before this change, Ctrl-C delivered SIGINT from the tty to `claude`/`opencode` **and every descendant in that group** - which was, in practice, the only thing that ever reached grandchildren. Now the tty signal reaches only clankerbar-cli; `signal.NotifyContext` (cmd/clankerbar/main.go:35) cancels ctx, and exec's default cancel is `Process.Kill` on the direct child alone. Neither adapter group-kills on plain caller cancellation: claude's group kill fires only from the ceiling branch, opencode's goroutine exists only when `sctx` carries a deadline (opencode.go:299).

Net effect: the change fixes "grandchildren survive an adapter kill" and simultaneously creates "grandchildren survive an operator Ctrl-C, and no longer even get SIGINT". It also makes claude/opencode behave differently from codex, which is still in the foreground group. This is reasoned from POSIX signal-delivery semantics plus the code paths, not executed end to end under a tty.

**Fix:** the same `cmd.Cancel` change above. `Cancel` runs for *any* `sctx` cancellation, deadline or caller, so Ctrl-C tears down the whole group. Worth deciding explicitly whether that path should be SIGTERM-then-SIGKILL rather than straight SIGKILL (see the low finding below).

### [MEDIUM] internal/harness/opencode.go:299-304 - the group kill fires after the process is reaped, on every capped session

`defer cancel()` (line 267) is what wakes the goroutine on the clean path, and it runs *after* `cmd.Run()` has already reaped the group leader. So every capped opencode session, including ones that finished successfully well inside the cap, ends with `kill(-pid, SIGKILL)` against a pid the kernel has released. Usually ESRCH; if the pid has been recycled onto a new group leader, this SIGKILLs an unrelated process group. On the normal path the window is microseconds, but when `sctx` is the *caller's* deadline context rather than one this function created - `cancel` is then the no-op `func(){}` from line 263, e.g. the resurrection probe's `pctx` at opencode.go:141 - the goroutine survives the function return and only fires when the caller cancels.

Secondary, and worth a deliberate decision rather than an accident: on the clean path this now SIGKILLs any descendant the session deliberately left running (a dev server, a background build), but only for opencode and only when a cap is set. claude does not do this.

**Fix:** covered by the `cmd.Cancel` change (os/exec only calls `Cancel` while the process is live). If the goroutine is kept for some reason, gate it on both a completion channel closed after `Run` returns and `sctx.Err() == context.DeadlineExceeded`.

### [MEDIUM] internal/harness/claude.go:124-131 - "lets Wait return promptly" is not actually guaranteed; claude still sets no WaitDelay

Verified experimentally: with the group kill disabled and a same-group descendant sleeping 25s, `claude.Invoke` blocked for **25.46s** - `cmd.Stderr` is an `io.MultiWriter`, so os/exec makes its own pipe and `Wait` waits on the copy goroutine with no WaitDelay to cut it short. The group kill closes that for descendants inside the group, but a descendant that calls `setsid` (exactly what a daemonising MCP server does at startup) is outside the group, survives `kill(-pgid)`, and hangs `Invoke` for as long as it lives - with no WaitDelay and no deadline anywhere on claude's session path, i.e. potentially forever, stalling the daemon. My attempt to demonstrate the escapee end to end was inconclusive: the `setsid` child lost the startup race against the kill and never ran, so I have verified the blocking half but not the escape half.

**Fix:** set `cmd.WaitDelay` on claude's session path too (opencode already does, opencode.go:292-294), so a holder that escapes the group cannot hang Invoke. Or, at minimum, amend the comment so it does not read as if the hang is now closed.

### [LOW] internal/harness/opencode.go:285-291 and internal/harness/wallclock_test.go:222-224 - comments the change falsified

Both still say the orphan is deliberately *not* killed and that the process group is "filed rather than smuggled in here" / "filed separately". opencode.go:285-291 sits five lines above the code that does exactly that. This repo treats comments as the primary documentation of intent, so leaving the pre-change rationale in place is more costly here than usual. Fix: rewrite both to say WaitDelay is now the backstop *behind* the group kill, not a substitute for it.

### [LOW] internal/harness/processgroup_test.go:66-72 - the elapsed bound is not a bound, and names the wrong fd

Two small things. (a) `if elapsed > 20*time.Second` is only evaluated *after* `Invoke` returns, so under the regression it is meant to catch the test does not fail at 20s - it hangs until the package timeout. Given the stub streams for 50s then `exec sleep 120`, a regression that stops the kill firing costs ~170s per run and, in a package that currently takes 26s, risks the 10-minute package timeout instead of a clean failure. Consider running Invoke in a goroutine with a `select` on a timer. (b) The comment blames "the grandchild's inherited **stdout** pipe"; stdout here is a `StdoutPipe`, which `Wait` closes without waiting on. The thing that actually blocks Wait is the **stderr** MultiWriter (claude.go:112) - verified above.

### [LOW] internal/harness/processgroup_unix.go:25 - SIGKILL with no grace for the whole subtree

The direct child was already SIGKILLed by CommandContext, so nothing changes for it, but descendants now die with no chance to clean up: a grandchild `git` leaves `index.lock`, a grandchild build leaves partial artefacts, and CLA-374's own scenario (a bash-tool build/test) is precisely that shape. opencode has a 5s WaitDelay budget that a SIGTERM-then-SIGKILL sequence could spend. Judgement call, not a defect - but it should be a stated choice.

### Nothing found at these

- **Non-unix split:** correct. `//go:build unix` covers the right set, `GOOS=windows` builds and vets clean, and the no-op degradation matches pre-change behaviour. The bar is unmet on Windows by construction, which the comment says plainly.
- **claude's kill path:** `groupKill` runs on the same goroutine as `Start`, after it, so no race there; ordering (group kill, then `cancel`) is right, and the ceiling/marker/exit-code handling at claude.go:141-151 is undisturbed.
- **Test quality:** both new tests genuinely fail under mutation, which the second commit's message documents honestly and which I reproduced. No padding findings here - the tests are better than the code they cover.
